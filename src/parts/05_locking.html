8Concurrency Control — Lock-Based Protocols

8.1 What is a concurrency-control protocol?

Definition
Concurrency-control protocols manage the sequence of read and write operations of concurrent transactions so that the resulting schedules are serializable (and preferably recoverable / cascadeless), i.e. the concurrent schedule has no inconsistencies. The DBMS component that does this is the concurrency-control manager (scheduler).

Families of protocols:

  • Lock-based protocols — 2PL, strict 2PL, rigorous 2PL, conservative 2PL (syllabus); graph/tree protocol.
  • Timestamp-based protocols — timestamp ordering, Thomas’ write rule (Section 10).
  • Validation-based (optimistic) protocols, multiversion schemes (Section 10).

8.2 Locks: Shared and Exclusive

Definition — Lock
A lock is a variable associated with a data item that controls access to it. In a lock-based protocol, a transaction cannot read or write a data item until it acquires an appropriate lock on it. (“If I have locked A, no one else can use it in a conflicting way.”)

Two lock modes:

  1. Shared lock (S) — lock-S(Q) / read-lock. A transaction holding S on Q can only read Q, not write it. Many transactions can hold S on the same item at the same time.
  2. Exclusive lock (X) — lock-X(Q) / write-lock. A transaction holding X on Q can both read and write Q. No other transaction can hold any lock on Q at the same time.

unlock(Q) releases the lock.

A lock is granted only if it is compatible with all locks already held by other transactions on that item; otherwise the requester waits. Only S–S is compatible: if a transaction holds an exclusive lock, no lock of any kind can be granted to others.

{{svg:lockmgr}}
Lock conversion & automatic locks
  • Upgrade (S → X): a transaction that has read Q and now wants to write it converts its lock. Allowed only in the growing phase of 2PL.
  • Downgrade (X → S): allowed only in the shrinking phase.
  • In real systems the programmer doesn’t write lock instructions; the DBMS issues them automatically: on read(Q) it gets lock-S(Q), on write(Q) it gets lock-X(Q) (or upgrades), and it releases all locks at commit/abort.

8.3 Simplistic locking, and why it is not enough

Simplistic lock protocol (class): a transaction locks every data item before operating on it and may unlock it right after finishing the operation (e.g. after the write). Locks alone do not guarantee serializability, because nothing says when a transaction may unlock:

Every access was properly locked, yet T2 displays 250 instead of 300, because T1 unlocked B before it locked A and T2 slipped in between. We need rules about when locks may be released → locking protocols (2PL).

There is a trade-off: keeping items locked for very long makes everyone else wait; unlocking too early allows inconsistency. Two more dangers of locking are deadlock and starvation.

8.4 Pitfalls of locking: Deadlock and Starvation

Deadlock

Definition
A deadlock is a situation in which two or more transactions are each waiting indefinitely for a lock held by another transaction in the set, so none of them can continue its normal execution.
{{sched:deadlock1}}

T2 waits for T1 (to release A) and T1 waits for T2 (to release B): neither can ever proceed. The only solution is to roll back one (or both) of the transactions so that its locks are released. Rollback or deadlock is still preferred over inconsistency. Details in Section 9.

Starvation

Definition
Starvation occurs when a transaction has to wait for an indefinite period to acquire a lock (or keeps being rolled back), even though the rest of the system keeps making progress. Its execution is delayed, but it is not impossible.
{{sched:starve}}

T2 wants an X-lock on A, but a stream of transactions keeps getting S-locks (each compatible with the one before), so A is never free for T2.

Solution: grant locks on a first-come-first-served basis: a lock request should not be granted if an earlier request for the same item is still waiting in an incompatible mode. When T3 asks for S(A), T2 is already waiting, so T3 must queue behind T2. (“Jisne pehle maanga, usse pehle milna chahiye.”) For deadlock victims, count how many times a transaction has been rolled back and stop picking it.

8.5 Two-Phase Locking (2PL)

Definition — Basic 2PL
A transaction follows the two-phase locking protocol if it issues its lock and unlock requests in two phases:
  1. Growing phase — the transaction may obtain locks (and upgrade S → X) but may not release any lock.
  2. Shrinking phase — the transaction may release locks (and downgrade X → S) but may not obtain any new lock.

Principle: once a transaction has released (unlocked) any lock, it can never acquire another lock. All lock requests precede the first unlock.

{{svg:twopl}}
Lock point
The lock point of a transaction is the point at which it acquires its final lock (end of the growing phase). Right after it, the first release / downgrade can happen. Transactions in a 2PL schedule can be serialized in the order of their lock points.
Source note
The class notes define the lock point as “the first instance when a transaction releases or degrades a lock”. That is the boundary seen from the other side: the lock point is the last acquire, and the first release follows it. Either way it marks the switch from growing to shrinking.
Example (class) — both transactions are 2PL

T1 obtains S(A) and X(B) and only then releases A ⇒ two-phase. T2 obtains S(B) and X(A) and only then releases ⇒ two-phase. We check 2PL transaction-wise (each transaction individually must be two-phase), not data-item-wise.

Why 2PL guarantees conflict serializability (proof — asked in 2025 PYQ)

Theorem: every schedule produced by 2PL is conflict serializable

Step 1 — an edge means an unlock before a lock. Suppose the precedence graph has an edge Ti → Tj. Then Ti performed an operation on some item Q, and later Tj performed a conflicting operation on Q (at least one is a write). The two locks needed (S/X or X/S or X/X) are incompatible, so Tj could get its lock on Q only after Ti unlocked Q:   unlocki(Q) < lockj(Q).

Step 2 — assume a cycle. Suppose, for contradiction, all transactions obey 2PL and the graph has a cycle T1 → T2 → … → Tn → T1. Using step 1 for each edge, and the 2PL rule inside each transaction (every lock comes before every unlock):

unlock1(Q1) < lock2(Q1) < unlock2(Q2) < lock3(Q2) < … < unlockn(Qn) < lock1(Qn)

So T1 acquires a lock on Qn after it has released the lock on Q1 — T1 is not two-phase. Contradiction. Hence, if the graph has a cycle, at least one transaction violates 2PL; equivalently, if all follow 2PL, the graph is acyclic and the schedule is conflict serializable. ∎

Alternative form: step 1 gives LP(Ti) < unlocki(Q) < lockj(Q) ≤ LP(Tj), so every edge goes from a smaller lock point to a larger one. A cycle would need LP(T1) < LP(T1) — impossible. So the equivalent serial order is the order of lock points.

Properties / drawbacks of basic 2PL

  • ✔ Ensures conflict serializability.
  • ✘ Does not ensure freedom from deadlock (see 8.10 example).
  • ✘ Does not prevent cascading rollbacks, and can even produce non-recoverable schedules, because a transaction can unlock an item it wrote before it commits:
{{sched:twopl_nonrec}}

So basic 2PL solves the consistency problem of concurrency control but not the recovery problems. The variants below fix that.

8.6 Strict 2PL

Definition
Everything is the same as basic 2PL, plus: all exclusive (X) locks must be held by a transaction until it commits or aborts. Shared (S) locks may be released earlier (in the shrinking phase).
{{sched:strict}}
Correction
In the class notes, T1’s lock released after commit is written as unlock(A). T1 had already released A; the lock it must hold till commit is its X-lock on B, so it should read unlock(B). Also, T2 must take lock-S(B) before releasing A, or T2 would violate 2PL.
  • ✔ Conflict serializable (it is a special case of 2PL).
  • ✔ No transaction can read or overwrite an uncommitted value ⇒ schedules are strict, hence cascadeless and recoverable. This was exactly the solution we wanted for cascading rollbacks.
  • ✘ Deadlock is still possible:
{{sched:strictdead}}

8.7 Rigorous 2PL

Definition
All locks — both shared and exclusive — must be held until the transaction commits or aborts. It is a stricter version of strict 2PL.
{{sched:rigorous}}
  • ✔ Conflict serializable, strict, cascadeless, recoverable.
  • ✔ Transactions are serialized in the order in which they commit (whoever commits/unlocks first comes first), which makes it easy to reason about (and to use with replication).
  • ✘ Deadlock is still possible (the strict 2PL deadlock example is also rigorous).
  • ✘ Lowest concurrency of the three: even read locks are held to the end.
  • Most commercial DBMSs actually implement strict or rigorous 2PL.

8.8 Conservative (Static) 2PL

Definition
A transaction must acquire all the locks it needs before it starts executing, by predeclaring its read-set and write-set. If any of the needed locks is unavailable, it acquires none of them and waits, then tries again.
{{sched:conservative}}
  • ✔ Deadlock-free: a transaction never holds some locks while waiting for others (no “hold and wait”), so no circular wait can form. In the class example, T1 holding X(A) and waiting for X(B) while T2 holds X(B) and waits for X(A) simply cannot happen.
  • ✔ Locks can be released as soon as the transaction finishes using them (no forced delay until commit as in rigorous 2PL).
  • ✘ Needs advance knowledge of every item the transaction will access (hard with conditional logic/queries); otherwise it must lock more than needed → wastage of resources, low concurrency.
  • It is called static 2PL because the lock set is fixed (declared) before execution, unlike basic 2PL where locks are requested dynamically as the transaction runs.
  • No partial lock acquisition: suppose T1 holds X(A), X(B) and T2 needs X(B), X(C). Even though C is free, T2 does not lock C while it waits for B — it takes both together once B is released. So T2 never blocks anyone else while waiting.
  • ✘ Can still cause starvation (a transaction needing many popular items may never get all at once).
  • ✘ Not necessarily strict ⇒ cascading rollbacks possible unless combined with strict/rigorous; the serialization order is also less predictable than in rigorous 2PL.

Exam tip — writing 2PL answers
  • Always draw the growing/shrinking graph with the lock point marked.
  • When asked to “add lock and unlock instructions”, put every lock before the first unlock in each transaction, use lock-S for items only read and lock-X for items written (or lock-S then upgrade).
  • To show a deadlock, interleave so that each transaction holds one item and requests the other’s.
  • For “compare the variants”, reproduce the 8.9 table with a small schedule for each.
