6Schedules and Serializability

6.1 What is a schedule?

Definition — Schedule
When several transactions execute concurrently, the order in which their instructions are executed is called a schedule. A schedule contains all the instructions of the participating transactions and preserves the order of instructions within each individual transaction.

A complete schedule contains a commit or abort as the last action of every transaction. The concept of serializability of schedules is used to decide which schedules are correct when transactions’ operations are interleaved.

6.2 Types of schedules

The PDF lists four types: Serial, Non-serial, Conflict-serializable and View-serializable. By recoverability there are also Recoverable, Cascadeless and Strict schedules (Section 7). In total:

(a) Serial schedule

One transaction executes completely before the next one starts; after the first transaction finishes its cycle, the next is executed. With T1 and T2 there are two serial schedules (T1 then T2, or T2 then T1). Serial schedules are always correct.

(b) Non-serial schedule

If interleaving of operations is allowed, the schedule is non-serial: operations of each transaction are executed non-consecutively, interleaved with operations of the other transaction. A non-serial schedule may or may not be correct:

{{sched:nonserialC}}{{sched:nonserialD}}

Schedule C is incorrect (T1’s update of X is lost). Schedule D gives exactly the same result as serial schedule A, so it is correct. How do we tell them apart without computing values? That is what serializability does.

6.3 Serializability — the idea

Definition — Serializable schedule
A (non-serial) schedule is serializable if it is equivalent to some serial schedule of the same transactions. Since serial schedules are always consistent, a serializable schedule is also consistent — and it gets the speed benefits of concurrency.

“Equivalent” can be defined in three ways:

  1. Result equivalence — same final values. Not used, because it may hold “by accident” for particular input values.
  2. Conflict equivalence → conflict serializability (6.4 – 6.6). Most important.
  3. View equivalence → view serializability (6.7).
Class summary
If a concurrent schedule turns out to be serializable, we can be sure it gives consistent results, so we use it for its throughput and time efficiency. If it is not serializable, it may or may not be consistent, so we do not go ahead with it and look for an alternative (e.g. make a transaction wait).

6.4 Conflicting operations

Definition — Conflicting operations
Two operations in a schedule conflict if all three conditions hold:
  1. they belong to different transactions;
  2. they access the same data item;
  3. at least one of them is a write.

Non-conflicting operations (different items, or both reads) can be swapped without changing the result. Conflicting operations can never be swapped.

Swap rules in one line (class)
For the same variable: if even one write is involved, we cannot swap. We can swap: two reads of the same variable, or any two operations on different variables. (We also never swap two operations of the same transaction.)

6.5 Conflict serializability — swapping method

Definition
  • If a schedule S can be transformed into a schedule S′ by a series of swaps of non-conflicting instructions, then S and S′ are conflict equivalent.
  • A schedule is conflict serializable if it is conflict equivalent to a serial schedule, i.e. after swapping non-conflicting operations it can be transformed into a serial schedule.

The swapping method works instruction by instruction, one swap at a time. With 2 transactions, try to convert S into T1 → T2; if that fails, try T2 → T1.

Worked example 1 (class) — conflict serializable
{{sched:cs1}}

Goal: T1 → T2. We need to move T1’s read(B) and write(B) above T2’s read(A), write(A). They work on different variables (B vs A), so every swap is allowed:

  1. swap T1:read(B) with T2:write(A)
  2. swap T1:read(B) with T2:read(A)
  3. swap T1:write(B) with T2:write(A)
  4. swap T1:write(B) with T2:read(A)
{{sched:cs1_step1}}⇒{{sched:cs1_final}}

Result: S is conflict equivalent to the serial schedule T1 → T2 ⇒ S is conflict serializable.

Worked example 2 (class) — NOT conflict serializable
{{sched:cs2}}
  • Try T1 → T2: T1’s write(A) (step 5) must move above T2’s write(A) (step 3). Both write A ⇒ conflicting pair, cannot be swapped. ✗
  • Try T2 → T1: T1’s read(A) (step 1) must move below T2’s write(A) (step 3). read(A)/write(A) conflict ⇒ cannot be swapped. ✗

It is not equivalent to either serial schedule ⇒ not conflict serializable.

Worked example 3 (class) — “no combination possible”
{{sched:t346}}

T3 → T4 → T6 fails because T4’s write(Q) (step 2) would have to move after T3’s write(Q) (step 3) — a W–W conflict. Any other order fails similarly ⇒ not conflict serializable. (We will see in 6.7 that it is view serializable.)

6.6 Testing conflict serializability — the Precedence Graph

Swapping is slow and error-prone for big schedules. The simple and efficient method is to build a directed graph called the precedence graph (serialization graph, conflict graph).

Construction of the precedence graph G = (V, E)
  • V (vertices): one node for each transaction participating in schedule S.
  • E (edges): draw an edge Ti → Tj if an operation of Ti conflicts with and comes before an operation of Tj. Precisely, Ti → Tj if for some data item Q, one of these holds:
    1. Ti executes write(Q) before Tj executes read(Q)  (W–R)
    2. Ti executes read(Q) before Tj executes write(Q)  (R–W)
    3. Ti executes write(Q) before Tj executes write(Q)  (W–W)

The edge Ti → Tj means: in any equivalent serial schedule, Ti must come before Tj.

The test (theorem)
  • If the precedence graph has a cycle ⇒ S is NOT conflict serializable.
  • If the graph is acyclic ⇒ S is conflict serializable, and an equivalent serial order is obtained by a topological sort of the graph (repeatedly pick a node with no incoming edges). If there are several topological orders, each one is a valid equivalent serial schedule.

Cost: with n transactions, cycle detection takes O(n²) — polynomial, easy.

Step-by-step method (use this in the exam)
  1. Number the operations of the schedule in time order.
  2. Take each data item separately. List its operations in order.
  3. For each operation, look at every later operation on the same item by a different transaction; if at least one of the two is a write, add edge (earlier txn → later txn). Skip read–read pairs.
  4. Draw the graph (one edge per ordered pair, even if many conflicts create it).
  5. Look for a cycle. Cycle ⇒ not CS. No cycle ⇒ CS; write the topological order(s).

Common mistakes
  • Adding an edge for read–read pairs (they never conflict).
  • Adding edges between operations of the same transaction.
  • Only looking at adjacent operations — you must compare each operation with every later conflicting operation on that item.
  • Getting the direction wrong: the edge goes from the transaction whose operation comes first.
  • Forgetting that a cycle can be longer than two nodes (T1 → T2 → T3 → T1).
Notation note
The class notes sometimes write “serializable as T1 ← T2” to mean “T1 executes first, then T2”. These notes always write the serial order as T1 → T2 (arrow = “comes before”), which matches the precedence-graph edge direction.

6.7 View serializability

Conflict serializability is sufficient but not necessary for correctness: some schedules are correct but not conflict serializable. View serializability is a weaker (more permissive) notion, based on logic, not swaps: what does each transaction see, and what is the final result?

Definition — View equivalence
Two schedules S and S′ (on the same set of transactions) are view equivalent if, for every data item Q, these three conditions hold:
  1. Initial read: if transaction Ti reads the initial value of Q in S, then Ti must also read the initial value of Q in S′.
  2. Updated read (reads-from): if Ti executes read(Q) in S and that value was produced by write(Q) of Tj, then in S′ also Ti’s read(Q) must read the value produced by the same write(Q) of Tj.
  3. Final write: the transaction that performs the final write(Q) in S must also perform the final write(Q) in S′.

A schedule is view serializable if it is view equivalent to some serial schedule.

Conditions 1 and 2 ensure each transaction reads the same values in both schedules (so it computes the same things); condition 3 ensures the database ends in the same state.

Examples for each condition

Condition 1 — Initial read
{{sched:vi1}}{{sched:vi2}}

In S1, T1 reads the initial value of A. In S2, T1 reads the value written by T2. So S1 and S2 are not view equivalent.

Correction (notebook p. 119, PDF pp. 118 & 131)
The PDF shows exactly these two schedules and says they are view equivalent “because the initial read is done by T1 in both”. That is wrong: in S2, T2 writes A before T1 reads it, so T1’s read is no longer an initial read. A correct pair for condition 1 would have T1’s read before any write of A in both schedules.
Condition 2 — Updated read (PDF example, correct)
{{sched:vu1}}{{sched:vu2}}

In S1, T3 reads A updated by T2; in S2, T3 reads A updated by T1 ⇒ not view equal.

Condition 3 — Final write
{{sched:vf1}}{{sched:vf2}}

The final write of A is done by T3 in both ⇒ condition 3 is satisfied.

Clarification (notebook p. 120, PDF pp. 119 & 132)
The PDF concludes these are “view equal because the final write is by T3 in both”. Condition 3 is indeed satisfied, but to be view equivalent all three conditions must hold. Here condition 2 fails: in S1, T2 reads A written by T1; in S2, T2 reads the initial A. So, overall, S1 and S2 are not view equivalent. Use this pair only to illustrate condition 3.

Blind writes and the relation with conflict serializability

Key facts
  • Every conflict serializable schedule is also view serializable, but not vice-versa.
  • A blind write is a write(Q) by a transaction that has not read Q before writing it.
  • Every view serializable schedule that is not conflict serializable contains blind writes. (So: no blind writes + not CS ⇒ not VS either.)
Classic example — view serializable but not conflict serializable
{{sched:t346}}{{pgraph:t346}}

The precedence graph has a cycle T3 ⇄ T4 ⇒ not conflict serializable. Now compare with the serial schedule ⟨T3, T4, T6⟩:

{{sched:t346_serial}}
  1. Initial read: T3 reads the initial Q in both ✔
  2. Updated read: no transaction reads a value written by another transaction in either schedule ✔
  3. Final write: T6 writes Q last in both ✔

⇒ S is view equivalent to ⟨T3, T4, T6⟩ ⇒ view serializable. The writes of T4 and T6 are blind writes (they never read Q). T4’s write is “useless” — it is overwritten before anyone reads it — which is why the order with respect to it does not matter.

Class examples

(a) The schedule of worked example 1 (T1: R/W A, T2: R/W A, T1: R/W B, T2: R/W B) compared with serial T1 → T2: rule 1 ✔ (T1 reads the initial A and B in both), rule 2 ✔ (T2 reads A and B written by T1 in both — e.g. the pair “w1(A) → r2(A)” is preserved), rule 3 ✔ (T2 writes A and B last in both) ⇒ view serializable as T1 → T2.

(b) S: w1(t), w2(t), w1(t) — precedence graph has T1 ⇄ T2 ⇒ not conflict serializable. Compare with serial ⟨T2, T1⟩:

(c) S: w1(X), r2(X), w2(X), w1(X).

{{sched:vsno}}

Not conflict serializable (T1 ⇄ T2). View? T2 reads X written by T1 ⇒ T1 must come before T2. The final write is by T1 ⇒ T1 must come after T2. Contradiction ⇒ not view serializable either.

How to test view serializability in an exam
  1. Draw the precedence graph. If acyclic ⇒ CS ⇒ also VS. Done.
  2. If cyclic, check for blind writes. None ⇒ not VS.
  3. Otherwise write down the constraints: who reads initial values (must come before every writer of that item), the reads-from pairs (writer before reader, no other writer of that item in between), and the final writer of each item (must be the last among writers of that item). Find a serial order satisfying all of them (or show none exists).

Testing view serializability in general is NP-complete, which is why DBMSs use conflict serializability in practice.

Exam tip — “Why don’t we check view serializability ahead of conflict serializability?”
Because (1) testing VS is NP-complete while testing CS is a simple polynomial cycle check; (2) every CS schedule is already VS, so if the CS test passes we are done; (3) VS adds only schedules with blind writes, which are rare in practice; and (4) practical protocols (2PL, timestamp ordering) are designed to guarantee CS. So we always test CS first and look at VS only if CS fails and blind writes are present.
