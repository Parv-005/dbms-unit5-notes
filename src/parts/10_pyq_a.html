14.1 Transactions & ACID

Mid-Sem Sep 2024Q1(a)2 marks

How could the lack of support for ACID properties in a file system affect the reliability of data operations compared to a DBMS, especially in financial or transactional applications?

Show answer

A file system has no transaction manager, so none of the ACID guarantees exist:

  • No atomicity: if a program crashes after debiting account A but before crediting B, the half-done update stays in the files — money disappears. A DBMS rolls back the incomplete transaction using its log.
  • No consistency enforcement: rules like “balance ≥ 0” or “account must exist” must be coded in every program; one buggy program corrupts data. A DBMS enforces integrity constraints centrally.
  • No isolation: two programs updating the same file at the same time can overwrite each other (lost update, e.g. two simultaneous withdrawals both succeed on the old balance). A DBMS uses locking (2PL).
  • No durability: data written to OS buffers may be lost in a power failure even after the user was told “success”. A DBMS writes the commit record to a stable log and redoes lost committed work.

Hence for banking/payments a file system gives lost or duplicated money and inconsistent records, while a DBMS guarantees reliable, all-or-nothing, isolated and permanent transactions.

End-Sem (year not printed)Q1(b)(i)part of 4 marks

Briefly describe the following term with the help of an example: ACID properties.

Show answer

A transaction is a logical unit of work. To keep the database correct, every transaction must satisfy ACID. Example used throughout: transfer ₹100 from A (₹600) to B (₹300): read(A); A=A−100; write(A); read(B); B=B+100; write(B).

  • Atomicity — all operations happen or none. If the system fails after write(A) but before write(B), the DBMS undoes write(A), so we never end with A = 500, B = 300. (Recovery manager.)
  • Consistency — the transaction takes the DB from one consistent state to another: A + B = 900 before and after. (Programmer + integrity constraints.)
  • Isolation — concurrent transactions do not see each other’s intermediate results; e.g. a report summing A + B while the transfer is half-done must not see 800. Result equals some serial order. (Concurrency control.)
  • Durability — once committed, A = 500 and B = 400 survive even if the system crashes immediately afterwards. (Recovery manager, log.)

14.2 Concurrency problems

End-Sem 2026 SummerQ5(b)(i)part of 5 marks

Discuss the causes of Lost Update, Dirty Read, Non-repeatable Read, and Phantom Read with suitable examples.

Show answer

All four are caused by uncontrolled concurrent execution: operations of two transactions on the same data are interleaved without a concurrency-control protocol, so a conflicting operation sneaks in between.

1. Lost Update — cause: W–W conflict after both read

Two transactions read the same item and both write a new value computed from the old one; the later write overwrites the earlier, so one update is lost.

{{sched:lost}}

2. Dirty Read — cause: W–R conflict on uncommitted data

A transaction reads a value written by another transaction that has not committed; if the writer rolls back, the reader has used a value that never existed.

{{sched:dirty}}

3. Non-repeatable Read — cause: R–W conflict

A transaction reads the same item twice and another transaction updates (and commits) it in between, so the two reads differ.

{{sched:unrep}}

4. Phantom Read — cause: insert/delete by another transaction

A transaction re-runs a query with a condition; another transaction has inserted/deleted rows satisfying that condition, so new “phantom” rows appear (or rows vanish).

Mid-Sem Oct 2021Q4(c)4 marks

Explain the dirty read problem. How can we overcome the problem of dirty read? Explain with an example. Explain the difference between deadlock and starvation with the help of examples.

Show answer

Dirty read

A dirty read occurs when transaction T2 reads a data item written by T1 before T1 commits. If T1 later aborts, its write is undone, but T2 has already used the “dirty” value, which never officially existed.

{{sched:dirty}}

Overcoming it:

  • Allow a transaction to read an item only after the transaction that last wrote it has committed (cascadeless schedules).
  • Implement this with Strict 2PL: X-locks are held until commit/abort, so T2’s lock-S(X) is granted only after T1 commits. In the example, T2 would wait at step 4; when T1 aborts, X = 10 is restored and T2 reads the correct 10.
  • In SQL, use isolation level READ COMMITTED or higher.

14.3 Schedules & Serializability

End-Sem Nov–Dec 2023Q4(a)4 marks

Consider the following two transactions:
T1: read(A); read(B); if A = 0 then B := B + 1; write(B).
T2: read(B); read(A); if B = 0 then A := A + 1; write(A).
Let the consistency requirement be A = 0 ∨ B = 0, with A = B = 0 the initial values.
(i) Show that every serial execution involving these two transactions preserves the consistency of the database.
(ii) Show a concurrent execution of T1 and T2 that produces a nonserializable schedule.
(iii) Is there a concurrent execution of T1 and T2 that produces a serializable schedule?

Show answer

(i) Serial executions

Serial orderExecutionFinal A, BA = 0 ∨ B = 0 ?
T1 → T2T1: A = 0 so B := 1. T2: reads B = 1 ≠ 0, so A stays 0.A = 0, B = 1True (A = 0)
T2 → T1T2: B = 0 so A := 1. T1: reads A = 1 ≠ 0, so B stays 0.A = 1, B = 0True (B = 0)

Both serial executions preserve consistency.

(ii) A non-serializable concurrent execution

{{sched:p23_nonser}}

Both transactions read the initial values (A = 0, B = 0), so both perform their update: final A = 1, B = 1, which violates A = 0 ∨ B = 0. Precedence graph: r1(A) before w2(A) ⇒ T1 → T2; r2(B) before w1(B) ⇒ T2 → T1 — a cycle ⇒ not (conflict) serializable.

(iii) Is there a concurrent serializable execution?

No. A serializable schedule must be equivalent to T1 → T2 or T2 → T1.

  • For T1 → T2: there must be no edge T2 → T1, so T2’s read(B) must come after T1’s write(B). But write(B) is T1’s last instruction and read(B) is T2’s first, so T2 starts only after T1 has finished — that is the serial schedule itself.
  • For T2 → T1: symmetrically, T1’s first instruction read(A) must follow T2’s last instruction write(A) — again serial.

Hence every interleaved (truly concurrent) execution of T1 and T2 is non-serializable; only the two serial schedules are serializable.

(ii) Conflict serializable?

The graph has cycles. The simplest: T1 → T2 because w1(B) (step 4) precedes r2(B) (step 5), and T2 → T1 because w2(B) (step 6) precedes r1(B) (step 24). Others: T5 ⇄ T6 (r5(A) 32 → w6(A) 35 and r6(D) 12 → w5(D) 13), T3 ⇄ T6, T4 ⇄ T6, …

S is NOT conflict serializable.

(iii) Equivalent serial schedules

None exists. A conflict-equivalent serial schedule must order the transactions consistently with every edge (a topological order). Because of the cycle T1 → T2 → T1, T1 would have to come both before and after T2, which is impossible. So no serial schedule of T1…T6 is conflict equivalent to S.

(iv) Why not check view serializability first?

  • Testing view serializability is NP-complete (in the worst case we must try the n! serial orders), whereas testing conflict serializability needs only a precedence graph and cycle detection, which is polynomial (O(n²)).
  • Every conflict-serializable schedule is automatically view serializable, so if the cheap CS test succeeds, nothing more needs checking.
  • The extra schedules that are VS but not CS always contain blind writes, which are rare in practice, so the expensive test rarely helps.
  • Practical protocols (2PL, timestamp ordering) guarantee conflict serializability, so CS is what DBMSs actually enforce.

Extra (for completeness): S has blind writes, so one might ask whether it is view serializable. It is not: T2 reads B from T1 (steps 4 → 5) ⇒ T1 before T2; T1 reads B from T5 (21 → 24) ⇒ T5 before T1; T5 reads B from T6 (15 → 20) ⇒ T6 before T5; T6 reads C from T2 (11 → 22) ⇒ T2 before T6. That requires T2 < T6 < T5 < T1 < T2 — impossible.

14.4 Recoverability

End-Sem Nov–Dec 2023Q4(c)4 marks

What is a recoverable schedule? Why is recoverability of schedules desirable? Is every cascadeless schedule recoverable? Explain with an example.

Show answer

Recoverable schedule: a schedule in which, for every pair of transactions Ti, Tj such that Tj reads a data item previously written by Ti, the commit of Ti appears before the commit of Tj.

Why desirable: if a transaction fails, atomicity requires undoing it and every transaction that read its data. If such a dependent transaction has already committed, it can’t be undone (durability), and the database stays inconsistent. Recoverable schedules guarantee we never have to undo a committed transaction. Example of a non-recoverable schedule:

{{sched:nonrec}}

Making T9 wait to commit until after T8 makes it recoverable:

{{sched:rec}}

Is every cascadeless schedule recoverable? — Yes. In a cascadeless schedule, if Tj reads an item written by Ti, then Ti commits before Tj’s read. Tj can commit only after its own read, so: commit(Ti) < readj < commit(Tj). Hence Ti commits before Tj, which is exactly the recoverability condition. Example:

{{sched:cascadeless}}

Here T2 reads A only after T1 commits, and T3 only after T2 commits ⇒ cascadeless, and automatically recoverable (T1 commits before T2). The converse is not true: the recoverable schedule above (T9 reads uncommitted A) is not cascadeless.

Strict ⊂ Cascadeless ⊂ Recoverable — every cascadeless schedule is recoverable, but not every recoverable schedule is cascadeless.
