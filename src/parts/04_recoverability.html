7Recoverability of Schedules

Serializability assumed that no transaction fails. But transactions can abort. If T2 has read data written by T1 and then T1 aborts, T2 is working with garbage. Recoverability classifies schedules by how well they behave when a transaction fails.

Throughout this section: “Tj reads from Ti” means Tj reads a data item whose last write was done by Ti.

7.1 Non-recoverable schedule

Example (class, corrected)
{{sched:nonrec}}

T9 read A written by T8 and committed before T8. Now T8 fails and must be rolled back. To be atomic, T9 (which used T8’s value) should also be undone — but T9 has already committed and, by durability, a committed transaction cannot be rolled back. The database cannot be brought to a consistent state ⇒ non-recoverable. A DBMS must never allow such schedules.

Correction
The class notes write T9’s operation as read(B). For the example to make sense, T9 must read the item written by T8, i.e. read(A); otherwise T9 does not depend on T8 at all.

7.2 Recoverable schedule

Definition
A schedule is recoverable if, for every pair of transactions Ti and Tj such that Tj reads a data item previously written by Ti, the commit of Ti appears before the commit of Tj.
(The reader must commit only after the writer it read from has committed.)
{{sched:rec}}

Here T9 still reads uncommitted data, but it waits to commit until T8 commits. If T8 had aborted instead, T9 could still be rolled back because it had not committed. Why is recoverability desirable? Because without it, the failure of one transaction can leave committed transactions that depend on rolled-back data — the database becomes permanently inconsistent and atomicity/durability are violated.

7.3 Cascading rollback

A recoverable schedule can still be painful: if many transactions read from each other, one failure forces a chain of rollbacks.

Definition
Cascading rollback is the phenomenon in which a single transaction failure leads to a series of rollbacks of other transactions that read (directly or indirectly) its uncommitted data.
{{sched:cascade}}

T2 read A from T1, and T3 read A from T2. When T1 fails, T2 must roll back (it read T1’s value), and then T3 must roll back (it read T2’s value). The schedule is recoverable (nobody committed), but it causes a lot of undoing of work — undesirable and not ideal.

7.4 Cascadeless schedule (Avoids Cascading Aborts — ACA)

Definition
A schedule is cascadeless if, for every pair Ti, Tj such that Tj reads a data item previously written by Ti, the commit of Ti appears before the read operation of Tj.
In short: transactions read only committed data. (Class: “the child reads only after the parent has committed.”)
{{sched:cascadeless}}

T2 reads A only after T1 commits; T3 reads A only after T2 commits. If any transaction fails, nobody else has read its data ⇒ no cascading rollback.

Every cascadeless schedule is recoverable

Proof: In a cascadeless schedule, if Tj reads from Ti then ci comes before rj. Tj’s commit comes after its own read rj. So ci < rj < cj, i.e. Ti commits before Tj — which is exactly the recoverability condition. ∎

The converse is false: the recoverable schedule in 7.2 is not cascadeless (T9 reads uncommitted A).

Class note
Rollback (or even deadlock) is always preferred over an inconsistent schedule.

7.5 Strict schedule asked in 2026 PYQ

Definition
A schedule is strict if a transaction can neither read nor write a data item X until the last transaction that wrote X has committed or aborted.

Strictness is stronger than cascadeless: cascadeless forbids reading uncommitted data, strict also forbids overwriting uncommitted data.

{{sched:nostrict}}

Why does it matter? Undo restores a before-image. If T1 aborts after T2’s write, undoing T1 restores A to its value before T1, wiping out T2’s write. Strict schedules make recovery simple: to undo a transaction, just restore the before-images of its writes.

Recoverability is independent of serializability: a schedule can be serializable but non-recoverable, or recoverable but not serializable. A good DBMS wants schedules that are both conflict serializable and strict (or at least cascadeless). Strict 2PL (Section 8) produces exactly such schedules.

7.7 How to test a schedule — method

Step-by-step
  1. For every read rj(X), find the transaction Ti that last wrote X before it (ignore reads of initial values and reads of one’s own writes). List these “Tj reads from Ti” pairs.
  2. Recoverable? For each pair, check that Ti commits before Tj commits.
  3. Cascadeless? For each pair, check that Ti has already committed at the moment of the read.
  4. Strict? Additionally, for every write wj(X), the previous writer of X must have committed/aborted.
Example — 2026 end-sem schedule

r1(X); r2(Y); w1(X); r3(X); w2(Y); r1(Y); w3(X); c2; c1; c3

{{sched:p26}} {{recov:p26}}

T3 reads X from T1, and T1 commits (step 9) before T3 commits (step 10) ✔. T1 reads Y from T2, and T2 commits (step 8) before T1 (step 9) ✔ ⇒ recoverable. But both reads happen while the writer is still uncommitted ⇒ not cascadeless, hence not strict.

Exam tip
Whenever a question asks “recoverable / cascadeless / strict?”, make the small reads-from table shown above, then answer each of the three questions with a one-line justification quoting the step numbers.
