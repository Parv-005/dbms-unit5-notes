1Introduction to Transactions

1.1 What is a transaction?

Think of withdrawing money at an ATM or transferring money with UPI. To you it is one action (“send ₹100 to my friend”), but inside the database it is several steps: read your balance, subtract 100, write it back, read your friend’s balance, add 100, write it back. If the system stops half-way, you lose ₹100 and your friend gets nothing. A transaction is the DBMS’s way of saying: “treat all these steps as one single unit — either all of them happen, or none of them happen.”

Definition — Transaction
  • A transaction is a collection of operations that together form a single logical unit of work.
  • It is a unit of program execution that accesses and possibly updates various data items.
  • It is a logical unit of database processing that includes one or more database access operations (read, insert, delete, update).

Example: withdrawal + deposit of a money transfer is one transaction (1 unit of work).

A transaction usually starts with begin transaction and ends with end transaction (either a commit or a rollback/abort). Everything in between is the transaction.

1.2 The two basic operations: read(X) and write(X)

A transaction accesses data using two operations:

  1. read(X) — reads the value of data item X from the database and stores it in a buffer / local variable in main memory.
  2. write(X) — writes the value back from the buffer to the database.

All calculations (like X = X − 500) happen only on the local copy in memory. The database copy changes only when write(X) is executed.

Example from class — local copy vs database copy

Database has A = 500. Transaction executes read(A) → local A = 500. Then A = A − 100 → local A = 400. If we now look at the database, A is still 500, because the change happened only in local memory. Only after write(A) does the database get 400.

Example — a debit transaction (X = 4000)

Operations: R(X); X = X − 500; W(X)

Debit transaction T1 (initially X = 4000)
StepT1Remarks / values
1read(X)X = 4000 is copied from disk into the buffer

Now suppose the hardware, software or power fails after step 2 but before step 3. The 500 was subtracted only in the (volatile) buffer, so X in the database remains 4000 while the program thinks money was debited. Worse, in a transfer, money could be deducted from one account and never added to the other. This is why we need commit and rollback.

Correction (PDF p. 109)
The PDF says “X’s value will remain 400 in the database”. It should be 4000 (the original value), because the failed transaction never wrote 3500 back.
Beyond syllabus — read/write vs input/output (needed for Recovery)

Korth distinguishes two levels:

  • read(X) / write(X): move X between the transaction’s local variable and the buffer block in memory.
  • input(B) / output(B): move a whole block B between disk and the memory buffer.

So after write(X) the new value may still be only in memory; the buffer manager decides when to output it. A crash at that moment loses it. This gap is exactly what the log in Section 11 protects.

1.3 Commit and Rollback

Definition
  • Commit — saves the work done by the transaction permanently in the database. After commit, the changes are visible to others and can no longer be undone by rollback.
  • Rollback (Abort) — undoes all the work done by the transaction, restoring the database to the state it was in before the transaction started.

In SQL:

START TRANSACTION;                 -- or BEGIN
UPDATE account SET bal = bal - 100 WHERE acc_no = 'A';
UPDATE account SET bal = bal + 100 WHERE acc_no = 'B';
COMMIT;                            -- make both changes permanent
-- if anything goes wrong instead:  ROLLBACK;
-- SAVEPOINT s1;  ...  ROLLBACK TO s1;   (partial rollback, beyond syllabus)

1.4 Why do we need transactions? The two big problems

A DBMS must deal with two kinds of trouble:

Problem 1 — Failures
Hardware crash, power failure, software bug, disk failure, a transaction error (e.g. division by zero, insufficient balance). The database can be left half-updated.
Solved by: the recovery system (logs, undo/redo, checkpoints, shadow paging) → guarantees Atomicity & Durability.
Problem 2 — Concurrent execution
Many users run transactions at the same time on the same data. Their operations interleave and can interfere (lost updates, dirty reads …).
Solved by: the concurrency-control system (locking, 2PL, timestamps) → guarantees Isolation (and hence consistency).

The whole unit is about these two problems. The rules a transaction must obey are summarised by ACID.

2ACID Properties

Every transaction must have four properties, called ACID, to keep the database correct (consistent) before and after the transaction. Because of ACID, a transaction is always either fully completed or not done at all.

2.1 Atomicity — “all or nothing”

Definition
Either all operations of the transaction are reflected in the database, or none are. There is no midway; a transaction cannot happen partially. If any operation fails, the entire transaction is rolled back.

Atomicity involves two operations:

  • Abort: if a transaction aborts, none of its changes are visible.
  • Commit: if a transaction commits, all of its changes are visible.
Example — transfer ₹100 from A (₹600) to B (₹300)
Transaction T: transfer ₹100 from A to B (A = 600, B = 300)
StepTRemarks / values
1read(A)A = 600
2A = A − 100local A = 500
3write(A)database A = 500
4read(B)B = 300
5B = B + 100local B = 400
6write(B)database B = 400
7commitA + B = 900 before and after

If the transaction fails after write(A) but before write(B), ₹100 is deducted from A but never added to B: A = 500, B = 300, total = 800. ₹100 has vanished — an inconsistent state. Atomicity guarantees that the DBMS will undo the write to A (A goes back to 600), so the database looks as if the transaction never ran.

Who ensures it? The recovery manager, using the log to undo incomplete transactions.

2.2 Consistency — “valid state to valid state”

Definition
  • Execution of a transaction in isolation must preserve all integrity constraints, so the database is consistent before and after the transaction.
  • A transaction transforms the database from one consistent state to another consistent state; it leaves the database either in its prior stable state or a new stable state.
Example

Consistency rule for the transfer: A + B must stay the same.

Class example: A = 5000, B = 3000 (total 8000); transfer 1000 from A to B → A = 4000, B = 4000, total still 8000 → consistency maintained.

Other examples of consistency rules: balance ≥ 0, roll number unique (primary key), every enrolment refers to an existing student (foreign key).

Who ensures it? Mainly the application programmer (writing a correct transaction) together with the DBMS checking integrity constraints. Atomicity and isolation help: if every transaction is correct on its own, running them atomically and in isolation keeps the database consistent.

2.3 Isolation — “as if alone”

Definition
  • Even though many transactions execute concurrently, each transaction must behave as if it were executing alone — the result must be the same as some valid serial order.
  • Intermediate (uncommitted) results of a transaction must not be visible to other transactions. If T1 is using data item X, then T2 should not see X in a half-updated state until T1 ends.

Another everyday example: two people try to book the last seat on a train at the same moment. Without isolation both transactions could read “1 seat free” and both book it; with isolation the DBMS orders them so only one gets the seat.

Example from class — Alice and Bob

T1: Alice transfers ₹500 to Bob.   T2: Bob checks the total balance.

T1 (Alice → Bob)T2 (Bob checks)
① A = A − 500 (written)
③ read(A) — sees money already gone from A but not yet in Bob’s account
② … add 500 to B, commit

If T1 completes first and then T2 runs (serial order), Bob sees the correct total. But if T2 reads in the middle of T1 (before T1 commits), T2 sees a wrong value. Isolation prevents this.

Who ensures it? The concurrency-control subsystem of the DBMS (locking protocols, timestamps).

2.4 Durability — “committed means permanent”

Definition
After a transaction completes successfully (commits), the changes it made to the database persist, even if there is a system failure immediately afterwards. They cannot be lost by a faulty later transaction or by a crash. Later transactions see (and build on) these changes.
Example
You get the message “₹100 transferred successfully” and one second later the bank’s server crashes. When it restarts, your transfer must still be there. The recovery system redoes committed changes from the log if they had not yet reached the disk.

Who ensures it? The recovery subsystem (log on stable storage + redo).

Why a plain file system cannot give ACID (asked in mid-sem PYQ)

A program that updates ordinary files has no transaction manager: if it crashes after updating one file but not another, there is no automatic undo (no atomicity); there is no log to redo lost writes (no durability); two programs editing the same file at once can overwrite each other (no isolation); and constraints like “balance ≥ 0” must be coded by hand in every program (weak consistency). For banking / payments this means lost money, duplicated payments and corrupted data. A DBMS solves all of these with its recovery and concurrency-control components.

Mention which DBMS component ensures each property — examiners love that line.

3Transaction States

During its lifetime a transaction moves through several states. At any moment it is in exactly one of them.

3.1 The five states

  1. Active — the first state of every transaction. The transaction is executing its operations (reading / writing). E.g. inserting, deleting or updating records happens here, but nothing is permanently saved yet. From Active the transaction can go to Partially Committed or Failed.
  2. Partially Committed — the transaction has executed its final (last) statement, but its changes are still not confirmed permanently (they may still be only in main-memory buffers). E.g. in a “calculate total marks” transaction, the final display of the total is done in this state. A failure here can still send it to Failed.
  3. Committed — the transaction has completed successfully and all its effects are permanently saved in the database (the commit record is in the stable log). Once committed, rollback is not possible.
  4. Failed — normal execution can no longer proceed because of an error or failure (hardware/software problem, a check by the recovery system fails, e.g. the query to fetch marks cannot be executed).
  5. Aborted — the transaction has been rolled back and the database restored to its state before the transaction started. After aborting, the recovery module chooses one of two options:
    • Restart the transaction — if the abort was caused by hardware/software error or a deadlock that is not the transaction’s own fault. It is treated as a new transaction.
    • Kill the transaction — if it was due to an internal logical error (bad input, data not found, program bug) that will happen again if restarted.

A transaction that is either committed or aborted is said to be terminated.

TransitionWhen it happens
Active → Partially committedlast operation of the transaction has executed

Key point
Before commit there is always a chance of rollback; after commit, rollback is impossible. If a committed transaction was wrong, the only fix is to run a new compensating transaction (e.g. transfer the money back).
Observable external writes
Some actions cannot be undone — printing a receipt or dispensing cash at an ATM. A DBMS performs such “external writes” only after the transaction is committed, otherwise an aborted transaction may already have handed out money.
Exam tip
Always draw the state diagram with labelled arrows (it alone fetches half the marks), then one line per state, then restart vs kill.

4Serial, Concurrent and Parallel Execution

When several transactions are submitted, the DBMS can execute them in different ways. Your syllabus asks for concurrent versus parallel execution, and the class compared serial versus concurrent. We cover all three.

4.1 Serial execution

Definition
One transaction completes entirely before the next one begins. There is no interleaving of operations between transactions. For transactions T1 and T2 there are two serial orders: T1 → T2 or T2 → T1. For n transactions there are n! possible serial orders.
Advantages
  1. Always gives consistent results (each transaction sees a consistent database and leaves one).
  2. No confusion, no interference between transactions.
  3. Simpler recovery / rollback.
Disadvantages
  1. Poor resource utilisation — the CPU sits idle while a transaction waits for disk I/O.
  2. Low throughput (fewer transactions per unit time).
  3. Long waiting time — a short transaction must wait for a long earlier one to finish.

4.2 Concurrent execution

Definition
The operations of multiple transactions are interleaved: while one transaction waits (e.g. for disk I/O), the CPU executes an operation of another transaction, and so on. On a single CPU only one operation runs at a time, but the transactions appear to run simultaneously.
Advantages
  1. Higher throughput — more transactions completed per unit time.
  2. Better resource utilisation — CPU and disk work in parallel (while one works, the other is paused).
  3. Reduced average waiting / response time — short transactions don’t wait for long ones to finish.
Disadvantage
Results may or may not be consistent. The order of operations becomes very important: a bad interleaving causes lost updates, dirty reads, etc. (Section 5). Recovery also becomes complicated.
So what do we do?
We prefer concurrent execution, but with a correct order — one that is equivalent to some serial order. Such schedules are called serializable (Section 6), and the DBMS uses concurrency-control protocols (Section 8) to allow only those.

4.3 Concurrent vs Parallel execution

The words sound similar, but they are different:

  • Concurrent = transactions are in progress at the same time, their operations interleaved. Can happen on a single processor by time-slicing. It is about dealing with many things at once.
  • Parallel = operations physically execute at the same instant on multiple processors / cores / disks. It is about doing many things at once.

  • Inter-query parallelism: different queries / transactions run on different processors at the same time (increases throughput).
  • Intra-query parallelism: a single big query is split into parts that run in parallel (reduces response time), e.g. parallel sort, parallel join.

Every parallel execution is also concurrent, but not every concurrent execution is parallel.

5.1 The Lost Update problem

Definition
Two transactions read the same data item and then both update it based on the value they read. The second write overwrites the first, so the first transaction’s update is lost, as if it never happened. (Write–Write conflict.)
Example (X = 10; T1 adds 10, T2 adds 20)

5.2 The Dirty Read (Temporary Update) problem

Definition
A dirty read occurs when a transaction reads data that has been modified by another concurrent transaction that has not yet committed. If the first transaction then rolls back, the second transaction has read (and maybe used) a value that never officially existed. (Write–Read conflict.)
Example (X = 10)

T1 fails (e.g. server down) after T2 has read 20. T1’s change is undone (X = 10), but T2 has already computed and committed 40 from the dirty value 20. The database is now wrong, and because T2 already committed, it cannot be undone — a non-recoverable situation (Section 7).

How to overcome it (asked in PYQ):

  • A transaction should read a value only after the writing transaction has committed (“read only committed data”). Schedules that obey this are called cascadeless.
  • If the parent (writer) rolls back, the child (reader) must also roll back; to avoid this, the child should read only after the parent commits (class note).
  • In practice: use Strict 2PL — exclusive locks are held until commit, so nobody can read an uncommitted value; or set isolation level READ COMMITTED or higher.

Definition
A transaction reads the same data item twice and gets two different values, because another transaction modified (and committed) that item between the two reads. (Read–Write conflict.)

5.4 The Phantom Read problem

Definition
A transaction executes a query that returns a set of rows satisfying a condition; another transaction then inserts or deletes rows that satisfy that condition and commits. When the first transaction re-executes the same query, it sees new (“phantom”) rows appear, or some rows disappear.

Correction / clarification of the class example

In class, phantom read was shown as: T1 reads X, T2 reads X, T1 deletes X, and T2’s second read of X fails because X no longer exists.

That captures the idea that a row “vanishes”, but the precise textbook meaning is about a set of rows defined by a condition (a predicate) changing because of INSERT/DELETE by another transaction. The key difference:

  • Unrepeatable read — the same row shows a different value (caused by UPDATE).
  • Phantom read — the set of rows changes; new rows appear or old rows disappear (caused by INSERT / DELETE).

A phantom can also be caused by an UPDATE that makes an existing row start (or stop) satisfying the condition — e.g. T2 changes a student’s dept from 'CSE' to 'IT'; T1’s count of IT students goes up although no row was inserted.

Why it matters: locking the rows you have read does not prevent phantoms, because the new row did not exist when you took your locks. Preventing phantoms needs predicate / index (range) locking or the SERIALIZABLE isolation level.

6Schedules and Serializability

6.1 What is a schedule?

Definition — Schedule
When several transactions execute concurrently, the order in which their instructions are executed is called a schedule. A schedule contains all the instructions of the participating transactions and preserves the order of instructions within each individual transaction.

A complete schedule contains a commit or abort as the last action of every transaction. The concept of serializability of schedules is used to decide which schedules are correct when transactions’ operations are interleaved.

6.3 Serializability — the idea

Definition — Serializable schedule
A (non-serial) schedule is serializable if it is equivalent to some serial schedule of the same transactions. Since serial schedules are always consistent, a serializable schedule is also consistent — and it gets the speed benefits of concurrency.

“Equivalent” can be defined in three ways:

  1. Result equivalence — same final values. Not used, because it may hold “by accident” for particular input values.
  2. Conflict equivalence → conflict serializability (6.4 – 6.6). Most important.
  3. View equivalence → view serializability (6.7).
Class summary
If a concurrent schedule turns out to be serializable, we can be sure it gives consistent results, so we use it for its throughput and time efficiency. If it is not serializable, it may or may not be consistent, so we do not go ahead with it and look for an alternative (e.g. make a transaction wait).

6.6 Testing conflict serializability — the Precedence Graph

Swapping is slow and error-prone for big schedules. The simple and efficient method is to build a directed graph called the precedence graph (serialization graph, conflict graph).

Construction of the precedence graph G = (V, E)
  • V (vertices): one node for each transaction participating in schedule S.
  • E (edges): draw an edge Ti → Tj if an operation of Ti conflicts with and comes before an operation of Tj. Precisely, Ti → Tj if for some data item Q, one of these holds:
    1. Ti executes write(Q) before Tj executes read(Q)  (W–R)
    2. Ti executes read(Q) before Tj executes write(Q)  (R–W)
    3. Ti executes write(Q) before Tj executes write(Q)  (W–W)

The edge Ti → Tj means: in any equivalent serial schedule, Ti must come before Tj.

The test (theorem)
  • If the precedence graph has a cycle ⇒ S is NOT conflict serializable.
  • If the graph is acyclic ⇒ S is conflict serializable, and an equivalent serial order is obtained by a topological sort of the graph (repeatedly pick a node with no incoming edges). If there are several topological orders, each one is a valid equivalent serial schedule.

Cost: with n transactions, cycle detection takes O(n²) — polynomial, easy.

Step-by-step method (use this in the exam)
  1. Number the operations of the schedule in time order.
  2. Take each data item separately. List its operations in order.
  3. For each operation, look at every later operation on the same item by a different transaction; if at least one of the two is a write, add edge (earlier txn → later txn). Skip read–read pairs.
  4. Draw the graph (one edge per ordered pair, even if many conflicts create it).
  5. Look for a cycle. Cycle ⇒ not CS. No cycle ⇒ CS; write the topological order(s).

6.7 View serializability

Conflict serializability is sufficient but not necessary for correctness: some schedules are correct but not conflict serializable. View serializability is a weaker (more permissive) notion, based on logic, not swaps: what does each transaction see, and what is the final result?

Definition — View equivalence
Two schedules S and S′ (on the same set of transactions) are view equivalent if, for every data item Q, these three conditions hold:
  1. Initial read: if transaction Ti reads the initial value of Q in S, then Ti must also read the initial value of Q in S′.
  2. Updated read (reads-from): if Ti executes read(Q) in S and that value was produced by write(Q) of Tj, then in S′ also Ti’s read(Q) must read the value produced by the same write(Q) of Tj.
  3. Final write: the transaction that performs the final write(Q) in S must also perform the final write(Q) in S′.

A schedule is view serializable if it is view equivalent to some serial schedule.

Conditions 1 and 2 ensure each transaction reads the same values in both schedules (so it computes the same things); condition 3 ensures the database ends in the same state.

Because (1) testing VS is NP-complete while testing CS is a simple polynomial cycle check; (2) every CS schedule is already VS, so if the CS test passes we are done; (3) VS adds only schedules with blind writes, which are rare in practice; and (4) practical protocols (2PL, timestamp ordering) are designed to guarantee CS. 7Recoverability of Schedules

Serializability assumed that no transaction fails. But transactions can abort. If T2 has read data written by T1 and then T1 aborts, T2 is working with garbage. Recoverability classifies schedules by how well they behave when a transaction fails.

Throughout this section: “Tj reads from Ti” means Tj reads a data item whose last write was done by Ti.

Why does it matter? Undo restores a before-image. If T1 aborts after T2’s write, undoing T1 restores A to its value before T1, wiping out T2’s write. Strict schedules make recovery simple: to undo a transaction, just restore the before-images of its writes.

8Concurrency Control — Lock-Based Protocols

8.1 What is a concurrency-control protocol?

Definition
Concurrency-control protocols manage the sequence of read and write operations of concurrent transactions so that the resulting schedules are serializable (and preferably recoverable / cascadeless), i.e. the concurrent schedule has no inconsistencies. The DBMS component that does this is the concurrency-control manager (scheduler).

Families of protocols:

  • Lock-based protocols — 2PL, strict 2PL, rigorous 2PL, conservative 2PL (syllabus); graph/tree protocol.
  • Timestamp-based protocols — timestamp ordering, Thomas’ write rule (Section 10).
  • Validation-based (optimistic) protocols, multiversion schemes (Section 10).

8.2 Locks: Shared and Exclusive

Definition — Lock
A lock is a variable associated with a data item that controls access to it. In a lock-based protocol, a transaction cannot read or write a data item until it acquires an appropriate lock on it. (“If I have locked A, no one else can use it in a conflicting way.”)

Two lock modes:

  1. Shared lock (S) — lock-S(Q) / read-lock. A transaction holding S on Q can only read Q, not write it. Many transactions can hold S on the same item at the same time.
  2. Exclusive lock (X) — lock-X(Q) / write-lock. A transaction holding X on Q can both read and write Q. No other transaction can hold any lock on Q at the same time.

unlock(Q) releases the lock.

A lock is granted only if it is compatible with all locks already held by other transactions on that item; otherwise the requester waits. Only S–S is compatible: if a transaction holds an exclusive lock, no lock of any kind can be granted to others.

Lock conversion & automatic locks
  • Upgrade (S → X): a transaction that has read Q and now wants to write it converts its lock. Allowed only in the growing phase of 2PL.
  • Downgrade (X → S): allowed only in the shrinking phase.
  • In real systems the programmer doesn’t write lock instructions; the DBMS issues them automatically: on read(Q) it gets lock-S(Q), on write(Q) it gets lock-X(Q) (or upgrades), and it releases all locks at commit/abort.

8.5 Two-Phase Locking (2PL)

Definition — Basic 2PL
A transaction follows the two-phase locking protocol if it issues its lock and unlock requests in two phases:
  1. Growing phase — the transaction may obtain locks (and upgrade S → X) but may not release any lock.
  2. Shrinking phase — the transaction may release locks (and downgrade X → S) but may not obtain any new lock.

Principle: once a transaction has released (unlocked) any lock, it can never acquire another lock. All lock requests precede the first unlock.

Lock point
The lock point of a transaction is the point at which it acquires its final lock (end of the growing phase). Right after it, the first release / downgrade can happen. Transactions in a 2PL schedule can be serialized in the order of their lock points.
Source note
The class notes define the lock point as “the first instance when a transaction releases or degrades a lock”. That is the boundary seen from the other side: the lock point is the last acquire, and the first release follows it. Either way it marks the switch from growing to shrinking.

Why 2PL guarantees conflict serializability (proof — asked in 2025 PYQ)

Theorem: every schedule produced by 2PL is conflict serializable

Step 1 — an edge means an unlock before a lock. Suppose the precedence graph has an edge Ti → Tj. Then Ti performed an operation on some item Q, and later Tj performed a conflicting operation on Q (at least one is a write). The two locks needed (S/X or X/S or X/X) are incompatible, so Tj could get its lock on Q only after Ti unlocked Q:   unlocki(Q) < lockj(Q).

Step 2 — assume a cycle. Suppose, for contradiction, all transactions obey 2PL and the graph has a cycle T1 → T2 → … → Tn → T1. Using step 1 for each edge, and the 2PL rule inside each transaction (every lock comes before every unlock):

unlock1(Q1) < lock2(Q1) < unlock2(Q2) < lock3(Q2) < … < unlockn(Qn) < lock1(Qn)

So T1 acquires a lock on Qn after it has released the lock on Q1 — T1 is not two-phase. Contradiction. Hence, if the graph has a cycle, at least one transaction violates 2PL; equivalently, if all follow 2PL, the graph is acyclic and the schedule is conflict serializable. ∎

Alternative form: step 1 gives LP(Ti) < unlocki(Q) < lockj(Q) ≤ LP(Tj), so every edge goes from a smaller lock point to a larger one. A cycle would need LP(T1) < LP(T1) — impossible. So the equivalent serial order is the order of lock points.

9Deadlock Handling

9.1 Deadlock in DBMS

Definition
  • A deadlock is a condition where two or more transactions are waiting indefinitely for one another to give up locks.
  • A system is in a deadlock state if there is a set of transactions such that every transaction in the set is waiting for another transaction in the set.
Example (PDF) — Student and Grade tables

T1 holds a lock on some rows of the Student table and needs to update some rows of the Grade table. Simultaneously, T2 holds locks on those rows of the Grade table and needs to update the Student rows held by T1. T1 waits for T2, T2 waits for T1 — all activity comes to a halt and remains at a standstill.

A deadlock can occur only if all four Coffman conditions hold at the same time from OS, useful:

  1. Mutual exclusion — an X-locked item can be held by only one transaction.
  2. Hold and wait — a transaction holds some locks while waiting for others.
  3. No preemption — a lock cannot be forcibly taken away from a transaction.
  4. Circular wait — T1 waits for T2, T2 for T3, …, Tn for T1.

Prevention schemes work by making sure at least one of these never holds.

9.3 Deadlock prevention

(a) Pre-declaration — Conservative 2PL

Each transaction locks all the data items it needs before it begins execution: either all are locked in one step or none are. This removes “hold and wait”. Drawbacks: hard to know in advance which items are needed, and data items stay locked long before they are used → low utilisation.

(b) Ordering of data items

Impose a total order on all data items (e.g. by address/ID) and require every transaction to lock items only in that increasing order. A cycle of waits would need someone to request a “smaller” item while holding a “larger” one, which is forbidden ⇒ no circular wait. (The tree/graph-based protocol is a variant of this.)

(c) Timestamp-based prevention with preemption: Wait–Die and Wound–Wait

Every transaction gets a timestamp TS when it starts (smaller TS = older). When Ti requests a lock held by Tj:

Wait–Die (non-preemptive)
  • If TS(Ti) < TS(Tj) — Ti is older → Ti waits.
  • Otherwise — Ti is younger → Ti dies (is rolled back) and restarts later with its original timestamp.

Older waits for younger; younger never waits for older.

Wound–Wait (preemptive)
  • If TS(Ti) < TS(Tj) — Ti is older → Ti wounds Tj (Tj is rolled back, releasing the lock).
  • Otherwise — Ti is younger → Ti waits.

Younger waits for older; older never waits for younger.

Example

T5 (TS = 5), T10 (TS = 10), T15 (TS = 15).

  • T5 requests an item held by T10: wait-die → T5 (older) waits; wound-wait → T5 wounds T10 (T10 rolled back).
  • T15 requests an item held by T10: wait-die → T15 (younger) dies; wound-wait → T15 waits.

Why no deadlock? In wait-die, waits only go from older to younger; in wound-wait, only from younger to older. Either way the waits follow one direction of the timestamp order, so a cycle is impossible.

(d) Other simple schemes

  • No-waiting: if a lock cannot be granted immediately, abort the requester at once (and restart after a delay).
  • Timeout-based: a transaction waits for a lock at most a fixed time; then it is rolled back. Simple, but the time is hard to choose: too long wastes time, too short causes unnecessary rollbacks (and possible starvation).

9.4 Deadlock detection — the wait-for graph

Wait-for graph
  • One node per active transaction.
  • An edge Ti → Tj means Ti is waiting for Tj to release a lock on an item Ti needs. The edge is added when the request is blocked and removed when the lock is granted.
  • The system is in a deadlock if and only if the wait-for graph contains a cycle; every transaction on the cycle is deadlocked.

The detection algorithm is run periodically. How often depends on how frequently deadlocks occur and how many transactions they affect; if deadlocks are frequent, run it more often.

Don’t mix up the two graphs
Precedence graph (Section 6): edges from conflicting operations; a cycle means not serializable.
Wait-for graph: edges from blocked lock requests; a cycle means deadlock.

9.5 Recovery from deadlock

  1. Select a victim — roll back the transaction(s) that incur the minimum cost. Factors: how long it has run and how much longer it needs; how many data items it has used and how many more it needs; how many transactions would be involved in the rollback (cascades).
  2. Rollback — total rollback (abort and restart) or partial rollback (roll back only as far as needed to release the required lock, which requires extra bookkeeping).
  3. Avoid starvation — the same transaction must not be picked as victim every time. Include the number of rollbacks in the cost factor.

9.6 Deadlock and starvation in 2PL — summary

  • Basic, strict and rigorous 2PL all allow deadlocks: a transaction holds some locks (growing phase) and waits for others. 2PL ensures serializability, not deadlock freedom.
  • Handling: (i) prevent with conservative 2PL, item ordering, wait-die or wound-wait; or (ii) detect with a wait-for graph and roll back a victim; or (iii) use timeouts.
  • Starvation in 2PL arises from unfair lock granting (a stream of S-locks blocking an X-request) or repeatedly choosing the same deadlock victim. Fix: FCFS lock queues, aging, counting rollbacks, timestamp schemes that keep the original timestamp.
  • Strict 2PL with respect to deadlock: it still deadlocks, but deadlock recovery is cheap and clean: since no other transaction has read the victim’s uncommitted writes (X-locks were held), aborting the victim never causes cascading rollbacks. That is why real systems use strict 2PL + deadlock detection (or timeouts).

10Other Concurrency-Control Protocols beyond syllabus

Not in your syllabus list, but they are in Korth and often appear in viva/competitive exams. A short and complete overview:

10.1 Timestamp-ordering protocol

Instead of locks, order transactions by their start time. Each transaction Ti gets a unique timestamp TS(Ti). Each data item Q keeps:

  • W-timestamp(Q) — largest TS of any transaction that wrote Q successfully;
  • R-timestamp(Q) — largest TS of any transaction that read Q successfully.
Rules

Ti issues read(Q):

  • If TS(Ti) < W-timestamp(Q): Ti wants a value already overwritten by a younger transaction → reject; roll back Ti.
  • Else: execute; R-timestamp(Q) = max(R-timestamp(Q), TS(Ti)).

Ti issues write(Q):

  • If TS(Ti) < R-timestamp(Q): a younger transaction already read the old value → reject; roll back Ti.
  • If TS(Ti) < W-timestamp(Q): Ti’s write is obsolete → reject; roll back Ti.
  • Else: execute; W-timestamp(Q) = TS(Ti).

A rolled-back transaction restarts with a new timestamp.

  • ✔ Conflict serializable (equivalent serial order = timestamp order). ✔ Deadlock-free (no transaction ever waits).
  • ✘ Possible starvation of long transactions that keep restarting. ✘ Can generate non-recoverable / cascading schedules unless extended (e.g. buffer all writes until commit).

Thomas’ write rule: in the case TS(Ti) < W-timestamp(Q) for a write, simply ignore the obsolete write instead of rolling back. This allows some view-serializable (non-conflict-serializable) schedules, like the T3/T4/T6 blind-write schedule.

10.2 Validation-based (optimistic) protocol

Assumes conflicts are rare. Each transaction runs in three phases: (1) Read phase — read data and compute on local copies; (2) Validation phase — check that its reads/writes don’t conflict with transactions that committed during its lifetime; (3) Write phase — if validation succeeds, copy local updates to the database, else restart. No locks, no deadlocks, no cascading rollbacks; good for read-mostly workloads.

10.3 Multiple-granularity locking

Data is a hierarchy (database → areas → files → records). Locking a whole file at once is cheaper than locking every record. To make this safe, intention locks are placed on ancestors:

  • IS (intention-shared): explicit S locks will be taken at a lower level.
  • IX (intention-exclusive): explicit X (or S) locks will be taken lower down.
  • SIX: the node is locked in S, and X locks will be taken lower down.

10.4 Multiversion schemes and snapshot isolation

Keep several versions of each item. A reader gets the version appropriate to its timestamp/snapshot, so reads never wait and never block writers. Used by PostgreSQL, Oracle and MySQL InnoDB (snapshot isolation). Snapshot isolation is fast but not fully serializable (it can allow a “write skew” anomaly).

10.5 Graph-based (tree) protocol

If data items are arranged in a tree and only X-locks are used: the first lock may be on any item; afterwards an item can be locked only if its parent is currently locked by the same transaction; items can be unlocked at any time; an item once unlocked cannot be relocked. Guarantees conflict serializability and freedom from deadlock (and need not be two-phase), but may lock more items than needed and does not by itself guarantee recoverability.

11Database Recovery

A computer system, like any device, can fail. When it does, information may be lost. The recovery system (recovery manager) is the part of the DBMS that restores the database to a consistent state after a failure. It is responsible for Atomicity (undo the effects of failed / incomplete transactions) and Durability (make sure the effects of committed transactions are never lost).

Every recovery scheme has two parts:

  1. Actions taken during normal processing to keep enough information for recovery (writing the log, taking checkpoints, backups).
  2. Actions taken after a failure to restore the database (undo / redo).

11.2 Storage types

Stable storage is an abstraction: in practice it is built by keeping copies on several non-volatile devices with independent failure modes (RAID mirroring, remote copies) and writing them carefully: write copy 1, and only after it succeeds write copy 2.

11.3 Why recovery needs both UNDO and REDO

Recall (Section 1) that write(X) changes only the buffer; the buffer manager writes blocks to disk (output) when it likes. At the moment of a crash:

  • an uncommitted transaction may already have some of its changes on disk → they must be UNDONE;
  • a committed transaction may still have some changes only in memory (lost) → they must be REDONE.

Definition — Log

Write-Ahead Logging (WAL)

WAL rules
  1. A log record must be written to stable storage before the corresponding data block is written to disk (so the old value is always available for undo).
  2. Transaction Ti enters the committed state only after its <Ti commit> record has been written to stable storage.
  3. Before <Ti commit> is written, all log records of Ti must already be on stable storage.

Undo and Redo operations

  • undo(Ti) — restores the value of every data item updated by Ti to its old value, scanning Ti’s log records backwards (from the last one to the first).
  • redo(Ti) — sets the value of every data item updated by Ti to its new value, scanning forwards.
  • Both are idempotent: executing them many times gives the same result as executing once. This matters because the system may crash again during recovery.

There are two main log-based techniques, depending on when updates reach the database.

11.5 Deferred database modification (NO-UNDO / REDO)

Idea
All writes of a transaction are recorded in the log, but the actual database is not updated until the transaction partially commits. Only after <Ti commit> is in the log are the deferred writes applied to the database.
  • Log record format needs only the new value: <Ti, X, Vnew> (old value not needed — the database never contains uncommitted data).
  • Recovery rule: after a crash, redo(Ti) for every transaction that has both <Ti start> and <Ti commit> in the log. Transactions without a commit record are simply ignored — nothing of theirs reached the database, so no undo is ever needed.

    • redo(Ti) if the log contains both <Ti start> and <Ti commit>.
  • Undo is done by scanning backwards; redo by scanning forwards. (Classic order: first undo all uncommitted transactions, then redo committed ones. Modern Korth: first redo everything — “repeat history” — then undo incomplete ones. For strict schedules both give the same final result.)

11.7 Commit point of a transaction

Definition
A transaction reaches its commit point when all its operations have executed successfully and the effect of all its operations has been recorded in the log, and finally the <Ti commit> record is force-written to stable storage. Beyond the commit point the transaction is committed and its effects are assumed permanent.

Role in recovery: the commit point is the dividing line between UNDO and REDO.

  • A transaction that has not reached its commit point at a crash → its effects must be undone (rolled back).
  • A transaction that has reached its commit point → its effects must be redone from the log if they did not reach the disk (durability).

The log is the only place that tells the recovery manager which side of the line each transaction is on.

11.8 Checkpoints

Problem without checkpoints: after a crash we would have to search the entire log to decide what to undo and redo. (1) This is very time-consuming. (2) Most transactions that need redoing have already written their updates to disk long ago — redoing them is harmless (idempotent) but wastes time.

Checkpoint — definition and procedure

A checkpoint is a point in time at which the DBMS forces everything to a known state, so that recovery can start from there instead of from the beginning of the log. To take a checkpoint (simple, non-fuzzy):

  1. Output all log records currently in main memory onto stable storage.
  2. Output all modified (dirty) buffer blocks to the disk.
  3. Output a log record <checkpoint L> onto stable storage, where L is the list of transactions active at the time of the checkpoint.

No updates are allowed while the checkpoint is in progress.

Recovery using a checkpoint:

  1. Scan the log backwards from the end to find the most recent <checkpoint L>.
  2. Only transactions in L, or that started after the checkpoint, need to be considered. Transactions that committed before the checkpoint already have all their updates on disk → ignore.
  3. For each such transaction: if <Ti commit> is in the log → redo(Ti); otherwise → undo(Ti) (immediate modification). With deferred modification, only redo.

Fuzzy checkpoints
The simple checkpoint stops all updates while dirty blocks are written. A fuzzy checkpoint writes <checkpoint L> first and lets transactions continue while dirty pages are flushed in the background; recovery then uses the last completed checkpoint. Used in real systems (ARIES).

11.9 The recovery algorithm (putting it together)

Transaction rollback during normal operation (Ti aborts): scan the log backwards; for each <Ti, X, V1, V2> write V1 to X and log a compensation (redo-only) record <Ti, X, V1>; when <Ti start> is reached, write <Ti abort>.

Recovery after a crash:

  1. Redo phase: find the last checkpoint; set undo-list = L. Scan forward: redo every update record <Ti, X, V1, V2> (and compensation record); add Ti to the undo-list on <Ti start>; remove it on <Ti commit> or <Ti abort>.
  2. Undo phase: scan backward from the end; for every log record of a transaction in the undo-list, restore the old value (writing compensation records); when <Ti start> is found, write <Ti abort> and remove Ti. Stop when the undo-list is empty.

11.10 Shadow paging

Idea
Shadow paging is a recovery technique that needs no log in a single-user environment. The database is divided into fixed-size pages, and a page table maps page numbers to disk blocks. Two page tables are kept during a transaction: the shadow page table (never modified) and the current page table.

How it works:

  1. When the transaction starts, the current page table is a copy of the shadow page table. The shadow table is saved on disk; a fixed disk location (the db-pointer) points to it.
  2. When the transaction writes a page for the first time, a copy of the page is written to an unused disk block, and the current page table entry is changed to point to the copy. All further changes go to the copy. The shadow page table and the old page are not touched.
  3. Commit: (i) flush all modified pages to disk; (ii) write the current page table to disk; (iii) atomically change the db-pointer to point to the current page table. The current table becomes the new shadow table.
  4. Crash / abort before step (iii): just discard the current page table. The db-pointer still points to the shadow table, which describes the database exactly as it was before the transaction → the database is consistent. Free the modified pages (garbage collection).

Hence shadow paging is a NO-UNDO / NO-REDO technique.

Advantages
  • No overhead of writing log records (single-user case).
  • Very fast recovery: no undo, no redo, no log scan — just keep the shadow table.
  • Simple to implement for single-user systems.
Disadvantages
  • Commit overhead: every commit must write many blocks (data pages + whole page table).
  • Data fragmentation: updated pages move to new locations, destroying locality (related pages no longer close together).
  • Garbage collection: old versions of pages become garbage and must be found and freed.
  • Hard to extend to concurrent transactions — logs and checkpoints are needed anyway.
  • Copying a large page table is expensive (needs a tree-structured page table).

11.11 Recovery from media (disk) failure

  • Periodically take an archival dump: copy the entire database to stable storage (tape / another site). During the dump: output log records and dirty blocks, copy the database, then write <dump> to the log.
  • After a disk failure: restore the database from the latest dump, then redo all transactions that committed after the dump using the log (which is on stable storage, so it survived).
  • Remote backup systems keep a live copy at another site by shipping log records continuously, for high availability.
ARIES in one paragraph
ARIES (used by IBM DB2, SQL Server) is the industrial recovery algorithm. Every log record has a log sequence number (LSN); every page stores the LSN of the last update applied to it (PageLSN), so redo is applied only if needed. It uses fuzzy checkpoints, a dirty-page table and a transaction table, and recovers in three passes: Analysis (find dirty pages and active transactions), Redo (repeat history from the right point) and Undo (roll back losers, writing compensation log records).
Exam tip
For log questions always: (1) state the technique (deferred / immediate), (2) write the log with the right record format, (3) for each crash point, list which transactions are committed (have a commit record) → redo, and which are not → undo (immediate) or ignore (deferred), (4) give the final values of every item.

12Database Security

Recovery protects data against failures; security protects it against people — unauthorised users, malicious insiders and attackers. The database often holds the most valuable data of an organisation (bank balances, medical records, passwords, exam results), so it is a prime target.

  • Confidentiality (secrecy) — information is not disclosed to unauthorised users. Loss example: leak of customers’ card numbers.
  • Integrity — information is modified only by authorised users in authorised ways. Loss example: an attacker changes a balance or a grade.

12.4 Control measures and the role of the DBA

Four main kinds of control (Elmasri):

  1. Access control — restrict who can access the system and what they can do (authentication + authorization).
  2. Inference control — prevent deducing individual information from statistical/aggregate queries.
  3. Flow control — prevent information flowing to unauthorised users (e.g. covert channels, MAC rules).
  4. Data encryption — protect sensitive data in storage and transmission.

The Database Administrator (DBA) is the central authority for security. Using a privileged (system/superuser) account, the DBA performs:

  • Account creation — creates user accounts and passwords;
  • Privilege granting — grants privileges to accounts;
  • Privilege revocation — takes privileges back;
  • Security-level assignment — assigns users to clearance levels (for MAC);
  • Monitoring the audit trail.

12.5 Authentication vs Authorization

Authentication — “Who are you?”
Verifying the identity of a user before allowing a connection. Methods: passwords (stored as salted hashes, never in plain text), multi-factor authentication (password + OTP), biometrics, smart cards, certificates, single sign-on (Kerberos/LDAP).
Authorization — “What may you do?”
Deciding which data and operations an authenticated user is allowed to access. Implemented by access-control models: DAC (GRANT/REVOKE), MAC (security levels), RBAC (roles).

Principle of least privilege: give every user/application only the minimum privileges needed for its job.

12.6 Discretionary Access Control (DAC) — GRANT and REVOKE

In DAC, the owner of an object (the user who created a table) has all privileges on it and can, at their discretion, grant privileges to other users, who may pass them on further.

Types of privileges

  • Account-level (system) privileges: CREATE TABLE, CREATE VIEW, ALTER, DROP, CREATE USER, SELECT ANY TABLE …
  • Relation-level (object) privileges on a specific table/view: SELECT, INSERT, UPDATE (optionally on specific columns), DELETE, REFERENCES (to create foreign keys referring to it), ALL PRIVILEGES.

GRANT

GRANT privilege_list ON object TO user_list | role | PUBLIC [WITH GRANT OPTION];

GRANT SELECT, INSERT ON Student TO U1;
GRANT UPDATE (marks) ON Result TO teacher1;        -- column-level
GRANT SELECT ON Employee TO U2 WITH GRANT OPTION;  -- U2 may grant SELECT to others
GRANT REFERENCES (dept_id) ON Department TO U3;

WITH GRANT OPTION lets the receiver propagate the privilege. Without it, the receiver can use the privilege but not pass it on.

REVOKE

REVOKE privilege_list ON object FROM user_list [CASCADE | RESTRICT];

REVOKE INSERT ON Student FROM U1;
REVOKE SELECT ON Employee FROM U2 CASCADE;   -- also revoke from everyone U2 granted it to
REVOKE SELECT ON Employee FROM U2 RESTRICT;  -- fail if U2 has granted it onwards
REVOKE GRANT OPTION FOR SELECT ON Employee FROM U2;  -- keep the privilege, remove the right to grant

Authorization (grant) graph and cascading revoke

Nodes are users; an edge Ui → Uj means Ui granted the privilege to Uj. A user has the privilege if and only if there is a path from the root (DBA / owner) to that user. Revoking with CASCADE removes the edge and then removes the privilege from every user who no longer has a path from the root. (A cycle of grants — U7 → U8 → U7 — doesn’t keep a privilege alive once the path from the root is gone.)

Views as a security mechanism

A view can hide columns (vertical restriction) or rows (horizontal restriction). Give users privileges on the view, not on the base table.

-- Clerks may see employee names and departments, but not salaries:
CREATE VIEW EmpPublic AS SELECT emp_id, name, dept FROM Employee;
GRANT SELECT ON EmpPublic TO clerk;

-- Each IT-department manager sees only IT employees:
CREATE VIEW IT_Emp AS SELECT * FROM Employee WHERE dept = 'IT';
GRANT SELECT ON IT_Emp TO it_manager;

Roles

CREATE ROLE faculty;
GRANT SELECT, UPDATE (marks) ON Result TO faculty;
GRANT faculty TO prof_sharma, prof_verma;   -- users inherit the role's privileges
REVOKE faculty FROM prof_verma;
Weakness of DAC
Once a user can read data, nothing stops them from copying it into their own table and granting that copy to anyone (e.g. via a Trojan-horse program). DAC controls access to objects, not the flow of information. MAC addresses this.

12.7 Mandatory Access Control (MAC)

Used in military, government and high-security systems. Every subject (user/program) gets a clearance and every object (table, row, even a column value) gets a classification from an ordered set of security classes:

Top Secret (TS) > Secret (S) > Confidential (C) > Unclassified (U)

Access is decided by the system’s rules, not by owners. The Bell–LaPadula model has two rules:

  1. Simple security property (no read up): subject S may read object O only if class(S) ≥ class(O).
  2. ★-property (star property, no write down): subject S may write object O only if class(S) ≤ class(O). This stops a Secret user from copying Secret data into an Unclassified table.

Multilevel relations attach a classification to each attribute value/tuple; users with different clearances see different versions of the same table. Polyinstantiation = several tuples with the same key but different classifications, so a low-level user isn’t tipped off that hidden data exists. beyond

12.8 Role-Based Access Control (RBAC)

Privileges are assigned to roles (job functions: student, faculty, accountant, DBA) and users are assigned to roles. When a person changes job, only their role membership changes. Supports least privilege and separation of duties (e.g. the person who creates a payment cannot also approve it). RBAC can model both DAC-like and MAC-like policies; SQL supports it with CREATE ROLE / GRANT role TO user.

12.9 SQL injection

Definition
SQL injection is an attack in which a user supplies input that is concatenated into an SQL statement, so that the input changes the meaning of the query. It can bypass login, read other users’ data, modify or delete tables.
Example

Application code builds the query by string concatenation:

query = "SELECT * FROM users WHERE name = '" + uname + "' AND pwd = '" + pwd + "'";

Attacker types username admin' -- (or password ' OR '1'='1). The query becomes:

SELECT * FROM users WHERE name = 'admin' --' AND pwd = '...'      -- rest is a comment
SELECT * FROM users WHERE name = 'x' AND pwd = '' OR '1'='1'        -- always true

The attacker logs in without a password. Input like '; DROP TABLE users; -- could destroy data.

Prevention:

  • Prepared statements / parameterised queries (the main defence): the query structure is fixed and inputs are passed as data, never as SQL. SELECT * FROM users WHERE name = ? AND pwd = ?
  • Input validation and escaping of special characters; stored procedures with parameters.
  • Least privilege for the application’s DB account (it should not be able to DROP tables).
  • Don’t show raw DB error messages to users; use web-application firewalls; audit and test.

12.10 Encryption

  • Encryption converts plaintext into ciphertext using a key, so stolen data is useless without the key.
  • At rest: encrypting database files/backups (Transparent Data Encryption — TDE), or individual sensitive columns (card numbers, Aadhaar).
  • In transit: SSL/TLS between client and server.
  • Symmetric (same key, e.g. AES — fast, for bulk data) vs asymmetric / public-key (public + private key, e.g. RSA — for key exchange and digital signatures).
  • Hashing (one-way, e.g. SHA-256/bcrypt with a salt) for storing passwords: the system compares hashes and never stores the password itself.
  • Key management is critical — keys must be stored separately from the data.

12.11 Auditing, and statistical database security

Audit trail: the DBMS logs who accessed what, when and from where (logins, queries on sensitive tables, privilege changes). If tampering is suspected, the audit trail is examined to find the responsible user. It also deters misuse (accountability). The audit log is like the recovery log but focused on users, not values.

Statistical databases allow only aggregate queries (COUNT, AVG …) e.g. census data. Attackers may infer individual values by combining queries: “average salary of female professors in dept X” when there is only one such person reveals her salary. Inference controls: refuse queries whose result set is smaller than a threshold (minimum query-set size), prevent queries with large overlap, add random noise to results, data swapping/partitioning.

12.12 Other important practices

  • Row-level security / Virtual Private Database: the DBMS automatically adds a predicate so each user sees only their rows.
  • Backups and recovery (availability) — encrypted and stored off-site.
  • Patching the DBMS and OS; disabling default accounts; firewalls allowing DB access only from application servers.

14.1 Transactions & ACID

Mid-Sem Sep 2024Q1(a)2 marks

How could the lack of support for ACID properties in a file system affect the reliability of data operations compared to a DBMS, especially in financial or transactional applications?

Show answer

A file system has no transaction manager, so none of the ACID guarantees exist:

  • No atomicity: if a program crashes after debiting account A but before crediting B, the half-done update stays in the files — money disappears. A DBMS rolls back the incomplete transaction using its log.
  • No consistency enforcement: rules like “balance ≥ 0” or “account must exist” must be coded in every program; one buggy program corrupts data. A DBMS enforces integrity constraints centrally.
  • No isolation: two programs updating the same file at the same time can overwrite each other (lost update, e.g. two simultaneous withdrawals both succeed on the old balance). A DBMS uses locking (2PL).
  • No durability: data written to OS buffers may be lost in a power failure even after the user was told “success”. A DBMS writes the commit record to a stable log and redoes lost committed work.

Hence for banking/payments a file system gives lost or duplicated money and inconsistent records, while a DBMS guarantees reliable, all-or-nothing, isolated and permanent transactions.

End-Sem (year not printed)Q1(b)(i)part of 4 marks

Briefly describe the following term with the help of an example: ACID properties.

Show answer

A transaction is a logical unit of work. To keep the database correct, every transaction must satisfy ACID. Example used throughout: transfer ₹100 from A (₹600) to B (₹300): read(A); A=A−100; write(A); read(B); B=B+100; write(B).

  • Atomicity — all operations happen or none. If the system fails after write(A) but before write(B), the DBMS undoes write(A), so we never end with A = 500, B = 300. (Recovery manager.)
  • Consistency — the transaction takes the DB from one consistent state to another: A + B = 900 before and after. (Programmer + integrity constraints.)
  • Isolation — concurrent transactions do not see each other’s intermediate results; e.g. a report summing A + B while the transfer is half-done must not see 800. Result equals some serial order. (Concurrency control.)
  • Durability — once committed, A = 500 and B = 400 survive even if the system crashes immediately afterwards. (Recovery manager, log.)

(iii) Equivalent serial schedules

None exists. A conflict-equivalent serial schedule must order the transactions consistently with every edge (a topological order). Because of the cycle T1 → T2 → T1, T1 would have to come both before and after T2, which is impossible. So no serial schedule of T1…T6 is conflict equivalent to S.

(iv) Why not check view serializability first?

  • Testing view serializability is NP-complete (in the worst case we must try the n! serial orders), whereas testing conflict serializability needs only a precedence graph and cycle detection, which is polynomial (O(n²)).
  • Every conflict-serializable schedule is automatically view serializable, so if the cheap CS test succeeds, nothing more needs checking.
  • The extra schedules that are VS but not CS always contain blind writes, which are rare in practice, so the expensive test rarely helps.
  • Practical protocols (2PL, timestamp ordering) guarantee conflict serializability, so CS is what DBMSs actually enforce.

14.4 Recoverability

End-Sem Nov–Dec 2023Q4(c)4 marks

What is a recoverable schedule? Why is recoverability of schedules desirable? Is every cascadeless schedule recoverable? Explain with an example.

Show answer

Recoverable schedule: a schedule in which, for every pair of transactions Ti, Tj such that Tj reads a data item previously written by Ti, the commit of Ti appears before the commit of Tj.

Why desirable: if a transaction fails, atomicity requires undoing it and every transaction that read its data. If such a dependent transaction has already committed, it can’t be undone (durability), and the database stays inconsistent. Recoverable schedules guarantee we never have to undo a committed transaction. Example of a non-recoverable schedule:

Basic 2PL: every transaction acquires all its locks (growing phase) before it releases any lock (shrinking phase). A schedule is conflict serializable iff its precedence (serializability) graph is acyclic.

Lemma. If the graph has an edge Ti → Tj, then Ti released some lock before Tj acquired a lock, i.e. for some item Q, unlocki(Q) < lockj(Q).
Proof: Ti → Tj means Ti executed an operation on Q, and later Tj executed a conflicting operation on Q (at least one is a write). Ti held a lock on Q for its operation, and Tj needs a lock on Q in a mode incompatible with Ti’s (S/X, X/S or X/X — only S/S is compatible). So Tj’s lock can be granted only after Ti releases its lock on Q. ∎

Theorem. Suppose the graph has a cycle T1 → T2 → … → Tn → T1. Apply the lemma to each edge:

  • T1 → T2: unlock1(Q1) < lock2(Q1)
  • T2 → T3: unlock2(Q2) < lock3(Q2)
  • …
  • Tn → T1: unlockn(Qn) < lock1(Qn)

Assume, for contradiction, that every transaction obeys 2PL. Then inside each Tk every lock precedes every unlock, so lockk(Qk−1) < unlockk(Qk). Chaining:

unlock1(Q1) < lock2(Q1) < unlock2(Q2) < lock3(Q2) < … < unlockn(Qn) < lock1(Qn)

Thus T1 acquires a lock on Qn after releasing its lock on Q1 — T1 violates 2PL, a contradiction. Hence if the graph has a cycle, at least one transaction does not obey 2PL. Equivalently, if all transactions obey 2PL, the graph has no cycle, and the schedule is conflict serializable. ∎

Corollary (serial order). Let LP(T) be the lock point. For every edge Ti → Tj: LP(Ti) ≤ unlocki(Q) < lockj(Q) ≤ LP(Tj). So transactions are serializable in the order of their lock points.

  • Grant lock requests in first-come-first-served order (a new S request waits behind an earlier waiting X request).
  • Aging — increase the priority of a transaction the longer it waits.
  • Include the number of times rolled back in the victim-selection cost so the same transaction isn’t always chosen.
  • Wait-die / wound-wait are starvation-free because a restarted transaction keeps its original (older) timestamp.

Describe any two techniques for deadlock prevention. Name the concurrency control protocol which generates deadlock-free schedules.

Each transaction Ti is given a timestamp TS(Ti) when it starts (smaller = older). Suppose Ti requests a lock held by Tj.

1. Wait–Die (non-preemptive)

  • If TS(Ti) < TS(Tj) (Ti older) → Ti waits.
  • Else (Ti younger) → Ti dies: it is rolled back and restarted later with the same timestamp.

Example: TS(T5)=5, TS(T10)=10. T5 requests an item held by T10 → T5 waits. T10 requests an item held by T5 → T10 dies.

2. Wound–Wait (preemptive)

  • If TS(Ti) < TS(Tj) (Ti older) → Ti wounds Tj: Tj is rolled back and the lock is given to Ti.
  • Else (Ti younger) → Ti waits.

Example: T5 requests an item held by T10 → T10 is rolled back. T10 requests an item held by T5 → T10 waits.

Why no deadlock: in wait-die only older transactions wait for younger ones; in wound-wait only younger wait for older. Waits always go in one direction of the timestamp order, so a cycle cannot form. Both avoid starvation because a restarted transaction keeps its old timestamp. (Other techniques: conservative 2PL / pre-declaration, ordering of data items, timeouts.)

Deadlock-free protocol: Conservative (static) 2PL — all locks are acquired before execution begins, so no transaction ever holds a lock while waiting for another. (The timestamp-ordering protocol and the tree protocol are also deadlock-free.)

Show answer

Purpose: in log-based recovery, after a crash the recovery manager would otherwise have to scan the whole log to decide which transactions to undo and redo. This is slow, and most of the redo work is unnecessary because old committed updates are already on disk. A checkpoint bounds the amount of log that must be processed.

Taking a checkpoint: (1) output all log records in main memory to stable storage; (2) output all modified buffer blocks to disk; (3) write <checkpoint L> to the log, L = list of active transactions.

Recovery with it: find the last checkpoint; transactions that committed before it are ignored; for transactions in L or started after it: redo if a commit record exists, else undo.

Example:

<T0 start> <T0, A, 1000, 950> <T0 commit>
<T1 start> <T1, B, 2000, 2050>
<checkpoint {T1}>
<T2 start> <T2, C, 700, 600> <T1 commit>
<T3 start> <T3, A, 950, 900> <T2 commit>   --- crash ---

T0 committed before the checkpoint → ignored (A = 950 already on disk). T1 and T2 committed after it → redo (B = 2050, C = 600). T3 has no commit → undo (A ← 950). Only the part of the log after the checkpoint (plus T1’s records) is processed.

How often? Often enough that crash-recovery time stays within an acceptable limit, but not so often that the overhead hurts normal processing — typically periodically (every few minutes) or after a fixed number of log records.

More frequent checkpoints
(i) Performance with no failureDecreases — each checkpoint forces log records and all dirty pages to disk and briefly halts updates; more checkpoints = more overhead.
(ii) Recovery time after a system crashDecreases — less log after the last checkpoint, fewer transactions to redo/undo.
(iii) Recovery time after a media (disk) failureEssentially unaffected — media recovery reloads the last archival dump and redoes the log since that dump; its time depends on how often dumps are taken, not on ordinary checkpoints.

Purpose of the system log

The system log (journal) is a sequential, append-only file on stable storage that records every operation of every transaction that affects the database. It lets the recovery manager (a) undo the effects of failed/incomplete transactions (atomicity) and (b) redo the effects of committed transactions whose updates were not yet on disk (durability). It also serves as an audit trail. Write-Ahead Logging: the log record is written before the data block, and the commit record before the transaction is declared committed.

Typical entries

<Ti start> / [start_transaction, T]transaction started
<Ti, X, old, new> / [write_item, T, X, old, new]update — before-image for undo, after-image for redo
[read_item, T, X]read (optional; for auditing / cascading-rollback checks)
<Ti commit>transaction committed
<Ti abort>transaction aborted / rolled back
<checkpoint L>checkpoint with list of active transactions

Role of the commit point

A transaction reaches its commit point when all its operations have executed and been recorded in the log, and its <Ti commit> record is force-written to stable storage. It is the boundary that tells recovery what to do: transactions past their commit point are redone (their effects must persist); transactions that had not reached it are undone (or ignored with deferred update). Without commit points, recovery could not distinguish completed work from partial work — reliability would be lost.

Role of checkpoints

A checkpoint forces log records and dirty buffers to disk and writes <checkpoint L>. During recovery only the log after the last checkpoint (plus active transactions in L) is examined; transactions committed before it are already on disk. It tells recovery where to start and makes recovery fast.

Why both are essential

  • Commit points ensure correctness/reliability: they decide undo vs redo for each transaction, guaranteeing atomicity and durability.
  • Checkpoints ensure efficiency: they limit how much log must be scanned and how much redo is done, so recovery time is short and predictable.
  • Without commit records, a checkpoint could not tell what to redo or undo; without checkpoints, commit records would still give a correct recovery but it would have to process the entire log — very slow.

Together: the log provides the information, commit points decide what to undo/redo, and checkpoints decide from where — giving recovery that is both reliable and efficient.

Explain checkpointing and log-based recovery.

Log-based recovery

The DBMS keeps a log on stable storage with records <Ti start>, <Ti, X, Vold, Vnew>, <Ti commit>, <Ti abort>, following Write-Ahead Logging (log before data).

  • Deferred modification (NO-UNDO/REDO): updates reach the database only after commit. Recovery: redo every transaction with both start and commit records; ignore the rest.
  • Immediate modification (UNDO/REDO): updates may reach the database before commit. Recovery: undo (backwards, restore old values) every transaction with start but no commit; redo (forwards, new values) every transaction with start and commit.
  • Undo/redo are idempotent, so a crash during recovery is harmless.

Example (immediate): log <T0 start> <T0,A,1000,950> <T0,B,2000,2050> <T0 commit> <T1 start> <T1,C,700,600> — crash. Redo T0 (A = 950, B = 2050), undo T1 (C = 700).

Checkpointing

To avoid scanning the entire log, the system periodically (1) flushes log records to stable storage, (2) flushes all dirty buffer blocks to disk, (3) writes <checkpoint L> (L = active transactions). After a crash, recovery begins from the last checkpoint: transactions committed before it are ignored; those in L or started later are redone if committed and undone otherwise.

Checkpointing trades a small overhead during normal operation for much faster recovery after a crash.

Shadow paging is a recovery technique that does not need a log (in a single-user environment). The database is divided into fixed-size pages; a page table with n entries maps the i-th page to its disk block.

  1. When a transaction starts, two page tables exist: the shadow page table (saved on disk, never changed during the transaction) and the current page table (a copy, kept in memory). A fixed disk location, the db-pointer, points to the shadow table.
  2. When the transaction writes page i for the first time, the page is copied to a free disk block, the current page table entry i is changed to point to the copy, and the update is made on the copy. The shadow table still points to the old page (in the figure, pages 2 and 5 were modified).
  3. Commit: flush the modified pages; write the current page table to disk; then atomically switch the db-pointer to the current page table, which becomes the new shadow table.
  4. Failure before commit: the db-pointer still points to the shadow page table, which describes the database before the transaction. Simply discard the current table and free the new pages. No undo, no redo.

Advantages: no log-record overhead; very fast recovery. Disadvantages: commit overhead (many blocks written), data fragmentation, garbage collection of old pages, difficult to extend to concurrent transactions.

  • Immediate: undo T2 backwards (B ← 350, A ← 550), redo T3 (B = 350) and T1 (A = 550, C = 250) ⇒ A = 550, B = 350, C = 250.

Final values if no failure occurs: A = 600, B = 400, C = 250.

Note: this schedule is not conflict serializable (r2(B) before w3(B) gives T2 → T3, and w3(B) before w2(B) gives T3 → T2), so a locking DBMS would not actually allow it. The question only asks for the log format.

End-Sem Nov–Dec 2022Q5(b)4 marks

What is meant by shadow paging? Explain its advantages and disadvantages.

Show answer

Shadow paging is a NO-UNDO/NO-REDO recovery technique. The database consists of fixed-size pages reached through a page table. During a transaction two page tables are maintained: the shadow page table, which is stored on disk and never modified, and the current page table, used by the transaction. When a page is modified for the first time it is written to a new disk block and only the current table is updated to point to it. To commit, the modified pages and the current page table are written to disk and the db-pointer is switched atomically to the current table. If the system fails before that, the shadow table still describes the old consistent database, so nothing needs to be undone or redone.

AdvantagesDisadvantages
  • No overhead of writing and maintaining log records (single-user)
  • Recovery is extremely fast — no undo, no redo, no log scan
  • Simple concept; a crash just means “keep using the shadow table”
  • Commit overhead — must flush all modified pages and the entire page table at each commit
  • Data fragmentation — updated pages move, so related pages are no longer contiguous (loss of locality)
  • Garbage collection — old page versions become unreachable garbage and must be reclaimed
  • Difficult to extend to concurrent transactions (needs logging anyway)
  • Large page tables are costly to copy
End-Sem Nov–Dec 2022Q5(c)4 marks

What are checkpoints? Explain the database recovery mechanism using checkpoints.

Show answer

Checkpoint: a point at which the DBMS writes all log records in memory and all modified buffer blocks to disk, and then writes a <checkpoint L> record (L = transactions active at that moment). Everything committed before the checkpoint is guaranteed to be on disk, so recovery need not look further back. Without checkpoints, the entire log would have to be scanned and many already-written updates would be needlessly redone.

Recovery mechanism (immediate modification):

  1. Scan the log backwards to the last <checkpoint L>.
  2. Undo-list = transactions in L + those starting after the checkpoint without a commit/abort record; redo-list = those in L or started later that have a commit record.
  3. Undo all transactions in the undo-list (scan backwards, restore old values, write <Ti abort>).
  4. Redo all transactions in the redo-list (scan forwards from the checkpoint, apply new values).
  5. Transactions that committed before the checkpoint are ignored.

In the figure: T1 → ignore; T2, T3 → redo; T4, T5 → undo. (With deferred modification only the redo step is needed.)

14.8 Database Security

End-Sem Nov–Dec 2025Q1(b) (first part)part of 5 marks

Discuss the terms “security of a database” and “integrity of a database” with the help of appropriate examples. (The second part of this question — relational vs hierarchical databases — belongs to Unit 1.)

Show answer

Security of a database means protecting the data against unauthorised access, disclosure, modification or destruction. It answers “who is allowed to do what?” and is enforced by authentication, authorization (GRANT/REVOKE, roles, views), encryption and auditing. It covers confidentiality, integrity and availability (CIA).
Example: in a university database, a student can view only their own marks (a view + SELECT privilege), only faculty have UPDATE on the marks column, and salaries are visible only to the accounts role. An outsider trying SQL injection on the login page must fail.

Integrity of a database means the data is accurate, valid and consistent — it obeys the rules of the real world. It answers “is this change correct?” and protects against accidental errors by authorised users. It is enforced by integrity constraints (domain, NOT NULL, UNIQUE, primary key, foreign key/referential integrity, CHECK), triggers, and ACID transactions.
Example: CHECK (marks BETWEEN 0 AND 100) rejects 105 entered by a teacher by mistake; a foreign key prevents enrolling a student roll number that doesn’t exist; a transfer is atomic so A + B stays constant.

End-Sem (year not printed)Q1(b)(iv)part of 4 marks

Briefly describe with the help of an example: GRANT and REVOKE.

Show answer

GRANT and REVOKE are SQL DCL commands implementing discretionary access control.

GRANT gives privileges (SELECT, INSERT, UPDATE, DELETE, REFERENCES, ALL) on an object to users or roles:

GRANT privileges ON object TO user | role | PUBLIC [WITH GRANT OPTION];
GRANT SELECT, INSERT ON Student TO U1;
GRANT UPDATE (marks) ON Result TO teacher WITH GRANT OPTION;

WITH GRANT OPTION allows the receiver to pass the privilege on to others.

REVOKE withdraws previously granted privileges:

REVOKE privileges ON object FROM user | role [CASCADE | RESTRICT];
REVOKE INSERT ON Student FROM U1;
REVOKE UPDATE (marks) ON Result FROM teacher CASCADE;

CASCADE also revokes the privilege from everyone who received it through that user (if they have no other path from the owner); RESTRICT refuses the revoke if such dependent grants exist.

Q1. Which ACID property ensures that a committed transaction survives a system crash?

  1. Atomicity
  2. Consistency
  3. Isolation
  4. Durability
Answer

D. Durability — ensured by the recovery manager through the log and redo.

Q2. Which pair of operations on the same item, by different transactions, does NOT conflict?

  1. Read–Write
  2. Write–Read
  3. Read–Read
  4. Write–Write
Answer

C. Read–Read — Two reads never conflict — the order doesn’t change what either sees.

  2. Dirty read
  3. Phantom read
  4. Deadlock

B. Dirty read — a W–R conflict on uncommitted data.

  1. Lost update
  2. Dirty read
  3. Non-repeatable read
  4. Phantom read

D. Phantom read — the set of rows satisfying the condition changed.
